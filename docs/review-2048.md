- 탭 순서: `My Blog` → `2048` → 테마 토글 → `New Game` → 보드. 합리적이다.

## 3. 발견 사항

### 3.1 `role="row"` 누락 — 사소 · **해결됨 (2026-08-15)**

> 수정 완료. `.board__row` 래퍼 4개에 `role="row"`를 주고 `display: contents`로 레이아웃에서 제거했다.
> 확인: 마크업에 `[role="row"]` 4개 / `[role="gridcell"]` 16개, 브라우저 실측으로 시각적 행 4 × 열 4 유지,
> UI가 찾는 셀 16개 그대로, 이동·타일 생성 정상, 코어 테스트 26/26.
> 아래는 원래 발견 내용이다.

`scripts/lib/templates.js:141-144` / 렌더된 마크업

보드는 `role="grid"`이고 셀 16개가 `role="gridcell"`인데, 그 사이 `role="row"` 계층이 없다(실측: `[role="row"]` 0개, `[role="gridcell"]` 16개).
ARIA 명세는 `grid` → `row` → `gridcell` 계층을 요구하므로, 엄밀히는 부적합이다.

**spec 내부의 모순이다.** §7은 행에 `role="row"`를 요구하지만 §8의 DOM 계약은 셀을 보드 직속 자식으로 두며, 후자는
`display: grid`가 요구하는 구조다. 에이전트 A가 이를 발견하고 임의로 고치지 않은 채 보고했다 — 지침대로 옳은 판단이다.

실질적 영향은 크지 않다. 이 게임에서 격자 구조 자체는 정보가 아니고(칸의 좌표를 읽을 이유가 없다), 상태는
`#game-status` 라이브 영역으로 전달되며 그쪽이 정상 동작한다.

**권고:** 고친다면 행 래퍼 `<div role="row">` 4개에 `display: contents`를 주면 레이아웃을 유지한 채 계층을 맞출 수 있다.
급하지 않다. 고칠 경우 templates.js(A 영역)와 game-2048.css(C 영역)를 함께 건드려야 한다.

### 4.1 승리 오버레이 — 확인 완료 (2026-08-15)

건드리지 않았고, 확인 후 `npm run build`로 되돌려 `WIN_VALUE = 2048`과 깨끗한 워킹 트리를 확인했다.

### 4.2 좁은 화면 · reduced-motion — 확인 완료 (2026-08-15)

**방법.** `resize_window`가 성공을 반환하면서도 뷰포트를 바꾸지 못했다. 대신 **같은 오리진의 iframe**을
지정 폭으로 만들어 게임 페이지를 로드하고 그 안에서 측정했다. iframe은 독립된 뷰포트를 가지므로 `vw` 단위와
미디어 쿼리가 그 폭 기준으로 계산된다 — CSS 추론이 아니라 실제 레이아웃 측정이다.

| 뷰포트 | 보드 폭 | 칸 크기 | 타일 글자 | 넘침 | 가로 스크롤 |
|---|---|---|---|---|---|
| 375px (iPhone) | 328px | 72px | 22.5px | 없음 | 없음 |
| 320px (iPhone SE) | 273px | 58px | 19.2px | 없음 | 없음 |

가장 불리한 조건 — 320px에서 네 자리 타일 `2048` — 도 확인했다. 글자 `scrollWidth`가 58px로 칸 폭과 같아
넘치지 않는다. `.tile--2048`에 걸린 작은 `clamp()`가 실제로 동작한다.

**reduced-motion.** CSSOM에서 미디어 규칙을 직접 찾아 확인했다:

```
condition: (prefers-reduced-motion: reduce)
rule:      .tile--new, .tile--merged { animation: ... none; }
```

조건과 대상 선택자가 맞고 브라우저가 규칙을 파싱했다. 다만 검사 환경이 해당 설정이 아니라
(`matchMedia('(prefers-reduced-motion: reduce)').matches === false`) 애니메이션이 멈추는 장면 자체는 보지 못했다.
§4의 미확인 항목으로 남긴다.

### 4.3 프라이빗 브라우징 (`localStorage` 예외) — 확인 완료 (2026-08-15)

**방법.** iframe 안에서 `Object.defineProperty`로 `localStorage` 게터가 항상 `SecurityError`를 던지게 만든 뒤,
그 상태에서 게임 스크립트를 로드했다. 실제 프라이빗 모드보다 가혹한 조건이다 — 읽기·쓰기 구분 없이 접근 자체가 실패한다.

| 항목 | 결과 |
|---|---|
| 자바스크립트 에러 | **0건** |
| 타일 렌더링 | 정상 (이동 후 3개) |
| 점수 · 라이브 영역 | 정상 (`Score 0, best 0.`) |
| 최고 점수 | `0` — 저장되지 않음 |

`try/catch`가 의도대로 동작한다. 저장소를 못 쓸 때 게임이 죽지 않고 **최고 점수 기억만 포기한다.**
spec §4가 요구한 열화 방식 그대로다.

## 5. 프로세스에 대한 기록

Review 서브에이전트를 띄웠으나 문서를 남기지 못했다. Work 단계의 에이전트 C도 같은 방식으로 두 번 멈췄다.

- C 1차: 30분간 파일 0개. 중단 시점 출력이 색상 대비 후보를 반복 시험하는 중이었다.
- C 2차: 파일은 냈으나(순서 강제가 통했다) 이후 52분간 색상만 다듬다 멈췄다. **당시 대비는 이미 5.63~15.92로 기준을 넘고 있었다.**
- Review: 29분간 파일 0개. 중단 직후 마지막 출력이 "검사를 모두 마쳤고 이제 문서를 쓰겠다"였다 — **끝나기 직전에 중단해 결과를 잃었다.** 부모 에이전트의 판단 착오다.

원인은 지침에 **완료 조건과 중단 기준이 없었던 것**이다. "대비 4.5:1을 확인하라"고만 쓰고 못 맞출 때 어떻게 하라는 말을 넣지 않아
무한 개선 루프가 열렸다. 2차 지침에 "두 번 조정해도 안 되면 실측값과 함께 미달로 보고하라"를 넣자 파일은 나왔다.

**다음 작업에 적용할 것:** 서브에이전트 지침에는 산출물 우선순위와 포기 조건을 명시한다. 그리고 오래 걸리는 에이전트를
중단할 때는 진행 정황을 먼저 확인한다 — 시간만 보고 끊으면 완성 직전의 결과를 버릴 수 있다.
