## 0. 전제 조건 (코드에서 확인한 제약)

`git show 54df309:CLAUDE.md`의 기술 제약은 코드에 그대로 살아 있다. 게임에도 예외 없이 적용된다.

| 제약 | 근거 | 어기면 |
|---|---|---|
| 브라우저 코드에 프레임워크·라이브러리 금지 | `package.json` devDependencies 3개는 모두 Node 전용, 번들러 없음 | 프로젝트 전제 붕괴 |
| 모든 경로는 `href(site, ...)`를 통과한 사이트 절대경로 | `scripts/lib/templates.js:15`, `scripts/build.js:23-36` | 로컬은 멀쩡, 배포 사이트(`/my-blog/`)에서만 404 |
| 테마 색은 `assets/css/variables.css` 커스텀 프로퍼티로만 | `variables.css` 헤더 주석, `layout.css` 전체가 토큰만 소비 | 다크 모드에서 조용히 대비 붕괴 |
| `dist/`는 매 빌드 통째 삭제 후 재생성 | `build.js:52` | 원본이 저장소에 없으면 게임이 사라짐 |
| 접근성: 시맨틱 태그, 진짜 `<button>`, `:focus-visible` | `base.css:83`에 전역 `:focus-visible` 이미 있음 | 키보드 사용자가 조작 불가 |

추가로 확인한 사실:

- `build.js`의 자원 처리는 `assets/css → dist/styles`, `assets/js → dist/scripts` 복사 두 줄이 전부다(`build.js:63-64`). **`assets/` 아래 css/js에 파일을 추가하면 빌드 스크립트 수정 없이 자동으로 배포된다.**
- 페이지 HTML은 전부 `baseLayout()`을 거친다. `baseLayout`은 현재 스타일시트 4개와 `theme-toggle.js`를 **하드코딩**하고 있어, 페이지별 추가 자원을 넣을 자리가 없다.
- `href()`는 `templates.js` 모듈 내부 함수이며 export되지 않는다. 게임 페이지 템플릿도 같은 파일 안에 있어야 `href()`를 쓸 수 있다.
- 인라인 head 스크립트가 `<html>`에 `js` 클래스를 붙인다(`templates.js:26`). `layout.css:46-50`가 이걸 이용해 JS 없을 때 토글 버튼을 숨긴다 — 게임의 no-JS 폴백에 그대로 재사용한다.
- 로컬 서버는 디렉토리 URL을 `index.html`로 해석한다(`serve.js:54`). `/games/2048/` 형태의 URL이 로컬·배포 모두에서 동작한다.

## 1. 배치 결정

### 안 A (추천) — 페이지는 `templates.js`가 생성, 자원은 기존 `assets/css`·`assets/js`에 추가

```
assets/css/game-2048.css        → dist/styles/game-2048.css   (기존 복사 규칙이 자동 처리)
assets/js/game-2048-core.js     → dist/scripts/game-2048-core.js
assets/js/game-2048-ui.js       → dist/scripts/game-2048-ui.js
scripts/lib/templates.js        → renderGamePage(site) 추가
scripts/build.js                → writePage 한 줄 추가
```

- 장점: 자원 복사 로직을 **건드리지 않는다**(빌드 수정은 페이지 1장 쓰는 한 줄뿐). 페이지가 `baseLayout()`을 거치므로 헤더·푸터·다크모드 선적용 스크립트·`href()` 경로 규칙을 전부 공짜로 상속한다. `BASE_PATH`도 자동으로 맞는다.
- 단점: 블로그 자원 디렉토리에 게임 파일이 섞인다. `game-2048.css`는 블로그 글 페이지에서 링크되지 않는데도 배포물에 포함된다(수 KB, 무시 가능).

### 안 B — `assets/games/2048/`에 정적 `index.html` 통째로 두고 복사

- 장점: 게임이 한 디렉토리에 모인다. 개념적으로 깔끔.
- 단점(치명적): 정적 HTML은 `href(site, ...)`를 통과할 수 없다. `BASE_PATH`가 주입되지 않아 CSS/JS 링크가 **배포 사이트에서만 404**가 난다. 헤더·푸터·다크모드 선적용 스크립트를 손으로 복제해야 하고, `baseLayout()`이 바뀌면 조용히 어긋난다. **채택하지 않는다.**

### 안 C — 페이지는 템플릿 생성, 자원만 `assets/games/2048/`에 분리

```
assets/games/2048/{game.css,core.js,ui.js}  → dist/games/2048/  (build.js에 fs.cp 한 줄 추가)
```

- 장점: 게임 자원이 블로그 자원과 섞이지 않고, 페이지와 자원이 같은 URL 아래 모인다.
- 단점: `build.js`의 자원 복사 목록이 3개로 늘어난다. 안 A 대비 얻는 것이 정리정돈뿐이다.

### 결론

**안 A를 채택한다.** 빌드 스크립트 수정 표면이 가장 작고, 경로 규칙 위반(가장 조용히 깨지는 실패)의 여지가 없다.

#### 구체적 수정 지점

1. `scripts/lib/templates.js` — `baseLayout`의 옵션 객체에 `extraStyles = []`, `extraScripts = []`를 추가(기본값이 빈 배열이므로 기존 두 호출부는 무수정). 기존 스타일시트 4줄 **뒤에** `extraStyles`를 `href(site, p)`로 감싸 렌더링하고, `theme-toggle.js` 뒤에 `extraScripts`를 `defer`로 렌더링한다. 순서가 중요하다: 게임 CSS는 토큰을 소비만 하므로 `variables.css` 뒤여야 하고, 게임 JS는 `core → ui` 순서여야 한다(`defer` 스크립트는 문서 순서대로 실행된다).
2. `scripts/lib/templates.js` — `renderGamePage(site)` export 추가. 게임 보드 마크업(§8 DOM 계약)을 `bodyHtml`로 넘기고 `extraStyles: ['/styles/game-2048.css']`, `extraScripts: ['/scripts/game-2048-core.js', '/scripts/game-2048-ui.js']`를 지정한다.
3. `scripts/build.js` — `renderGamePage` import 추가, `index.html` 작성 뒤에
   `await writePage(path.join(DIST_DIR, 'games', '2048', 'index.html'), renderGamePage(SITE));`

#### URL

| 환경 | URL |
|---|---|
| 로컬 (`npm run dev`) | `http://localhost:4321/games/2048/` |
| 배포 | `https://gietpa.github.io/my-blog/games/2048/` |

게임 페이지의 모든 자원 링크는 `/my-blog/styles/game-2048.css` 처럼 `BASE_PATH`가 붙은 형태여야 한다. 검증 방법은 §9.

#### 진입 링크 **[결정됨 — 헤더 nav에 추가]**

`baseLayout`의 `.site-nav` 안, 테마 토글 **앞에** `<a href="${href(site, '/games/2048/')}">2048</a>`을 넣는다.
모든 페이지(인덱스·글·게임)에 노출된다.

- `.site-nav`는 이미 flex라 항목 하나 추가로 레이아웃이 깨지지 않는다.
- 이 변경은 **전 페이지에 영향**을 준다. 리뷰에서 글 페이지 헤더도 함께 확인해야 한다.
- 링크 텍스트는 `2048`. 경로는 반드시 `href(site, ...)`를 통과시킨다.

## 2. 게임 규칙 **[필수]**

- 격자: **4 × 4 고정**. 코드는 `SIZE` 상수로 일반화하되 크기 변경 UI는 만들지 않는다.
- 시작: 빈 격자에 타일 2개 생성.
- 새 타일: **이동으로 격자가 실제로 바뀌었을 때만** 빈 칸 중 균등 확률로 1개 생성. 값은 **2가 90%, 4가 10%**.
  - "바뀌었을 때만"이 중요하다. 벽에 막혀 아무것도 안 움직였는데 타일이 생기면 플레이어는 손해 없이 패배한다.
- 승리: 값 2048 타일이 처음 생기는 순간. 오버레이로 알리고 **"계속하기"** 버튼을 제공한다(이후 승리 판정은 다시 뜨지 않는다).
- 패배: 빈 칸이 없고 **동시에** 가로·세로 인접한 같은 값 쌍이 하나도 없을 때. 빈 칸만으로 판단하면 꽉 찼지만 합칠 수 있는 판을 패배로 오판한다.
- 최대 타일: 상한을 두지 않는다(4096 이상도 계속 진행).

## 3. 이동·병합 알고리즘 **[필수]**

### 3.1 4방향을 따로 구현하지 않는다

한 줄을 미는 함수 `collapseLine`을 **하나만** 만들고, 4방향은 "줄을 어떤 순서로 읽어서 어디에 되쓰는가"로만 구분한다.

격자 회전/전치를 쓰지 않는 이유: 회전은 매 이동마다 격자 사본을 2~4번 만들고, 병합 위치를 UI에 알려주려면 회전을 역으로 되돌려야 해서 좌표 버그가 생기기 쉽다. **인덱스 생성만으로 같은 효과를 얻는다.**

```
lineIndices(direction, k):   # k번째 줄(행 또는 열)의 셀 인덱스를 "미는 방향의 벽에서 먼저" 순서로
  left  : [(k,0), (k,1), (k,2), (k,3)]
  right : [(k,3), (k,2), (k,1), (k,0)]
  up    : [(0,k), (1,k), (2,k), (3,k)]
  down  : [(3,k), (2,k), (1,k), (0,k)]
```

읽을 때와 되쓸 때 **같은 인덱스 배열**을 쓴다. 방향별 분기는 이 4줄이 전부다.

### 3.2 한 줄 밀기 의사코드 — 이중 병합 방지

이 프로젝트에서 가장 흔히 틀리는 지점이다. `[2,2,4]`를 왼쪽으로 밀면 `[4,4,0,0]`이지 `[8,0,0,0]`이 아니다. 한 번의 이동에서 이미 병합에 참여한 타일은 다시 병합되지 않는다.

```
collapseLine(line):                 # line[0]이 미는 방향의 벽에 가장 가깝다
  values = [v for v in line if v != 0]     # 1) 0 제거 (압축)
  out    = []
  gained = 0
  mergedSlots = []                          # 병합이 일어난 out 인덱스 (애니메이션용)
  i = 0
  while i < len(values):
    if i + 1 < len(values) and values[i] == values[i+1]:
      merged = values[i] * 2
      out.append(merged)
      gained += merged
      mergedSlots.append(len(out) - 1)
      i += 2                                # ★ 두 칸 건너뛴다 — 병합된 타일은 다음 비교에 참여하지 않는다
    else:
      out.append(values[i])
      i += 1
  pad out with 0 until len(out) == SIZE
  return { line: out, gained, mergedSlots }
```

이중 병합을 막는 장치는 **`i += 2` 한 줄**이다. `merged` 불린 배열을 따로 관리하는 흔한 구현보다 상태가 적어 틀릴 여지가 작다.

주의: 스캔은 **벽에 가까운 쪽부터** 진행해야 한다. `[2,2,2]`를 왼쪽으로 밀면 `[4,2,0,0]`이고 `[2,4,0,0]`이 아니다. `lineIndices`가 이 순서를 보장한다.

검증 케이스(§9 테스트에 그대로 들어간다):

| 입력 | 출력 | 획득 점수 |
|---|---|---|
| `[2,2,4,0]` | `[4,4,0,0]` | 4 |
| `[4,4,4,4]` | `[8,8,0,0]` | 16 |
| `[2,2,2,0]` | `[4,2,0,0]` | 4 |
| `[2,0,2,0]` | `[4,0,0,0]` | 4 |
| `[2,4,2,4]` | `[2,4,2,4]` (변화 없음) | 0 |
| `[0,0,0,2]` | `[2,0,0,0]` | 0 |

### 3.3 한 번의 이동

```
move(state, direction):
  next   = copy(state.grid)
  moved  = false
  gained = 0
  for k in 0..SIZE-1:
    idx = lineIndices(direction, k)
    result = collapseLine([next[i] for i in idx])
    for n, i in enumerate(idx):
      if next[i] != result.line[n]: moved = true
      next[i] = result.line[n]
    gained += result.gained
  if not moved: return { moved: false }          # 점수 변화도, 새 타일도 없다
  spawn = spawnTile(next, rng)
  return { grid: next, moved: true, gained, spawn, merged: [...] }
```

`rng`는 인자로 주입한다(기본 `Math.random`). 테스트에서 시드 고정 난수를 넣어 결정적으로 검증하기 위한 것이다.

## 4. 점수 **[필수]**

- 계산: 한 번의 이동에서 **생성된 병합 타일 값의 합**을 현재 점수에 더한다(`2+2 → 4` 이면 +4). 표준 2048 규칙.
- 표시: 현재 점수(Score)와 최고 점수(Best) 두 칸.
- 최고 점수: 현재 점수가 최고 점수를 넘는 즉시 갱신하고 `localStorage`에 저장한다.
- **키 이름: `my-blog:2048:best`**
  - 접두사를 붙이는 이유: GitHub Pages 프로젝트 사이트는 `gietpa.github.io` **오리진 전체**를 다른 저장소 사이트와 공유한다. `localStorage`는 오리진 단위이므로 `best` 같은 이름은 다른 프로젝트와 충돌할 수 있다. (기존 `theme` 키가 접두사 없이 쓰이고 있으나 이번 작업 범위에서 바꾸지 않는다.)
  - 저장·읽기는 **반드시 `try/catch`로 감싼다.** 프라이빗 브라우징에서 `localStorage` 접근이 예외를 던진다. `assets/js/theme-toggle.js:29-34`와 같은 패턴을 따른다. 예외가 나면 최고 점수 기억만 포기하고 게임은 정상 동작한다.
  - 읽은 값은 `Number()` 변환 후 유한한 0 이상 정수인지 검사한다(사용자가 손댈 수 있는 값이다).
- 진행 중인 판의 저장/복원은 **하지 않는다**(§10).

## 5. 입력

### 5.1 방향키 **[필수]**

- 리스너는 `document`가 아니라 **보드 요소**에 건다. 보드는 `tabindex="0"`으로 포커스 가능하게 만든다.
- 페이지 로드 시 보드에 프로그램적으로 포커스를 준다. 그래야 사용자가 클릭 없이 바로 방향키를 쓸 수 있다.
- `preventDefault()`는 **처리한 키(ArrowUp/Down/Left/Right)에 한해서만** 호출한다.
  - 이 설계의 이점: 보드에 포커스가 없으면 방향키가 원래대로 페이지를 스크롤한다. 문서 전역에서 방향키를 가로채면 게임 아래의 설명 텍스트를 키보드로 읽을 수 없게 된다.
- 이동 애니메이션 중 입력은 큐잉하지 않고 무시한다(구현 단순화, 체감 손해 없음).
- `key` 값으로 판정한다(`keyCode`는 폐기된 API).

### 5.2 WASD **[선택]**

한 줄 추가로 되지만 필수는 아니다. 넣는다면 도움말에 표기한다.

### 5.3 모바일 터치 — 스와이프 **[결정됨 · 필수]**

블로그가 모바일 우선 CSS를 쓰고 있어(`layout.css:1`) 터치 조작이 없으면 휴대폰에서 게임이 보이기만 하고 조작이 안 되는 화면이 된다. v1에 포함한다.

- `touchstart`/`touchend`의 좌표 차이로 판정. 임계값 **30px**, 가로/세로 중 **지배적 축 하나만** 채택한다.
- 임계값 미만의 움직임은 탭으로 보고 무시한다. 그래야 보드를 눌러 포커스를 주는 동작이 방향 입력으로 오인되지 않는다.
- 보드에 **`touch-action: none`을 반드시 준다.** 없으면 스와이프가 페이지 스크롤과 함께 먹혀 조작이 안 된다. 이 한 줄이 빠지면 데스크톱에서는 멀쩡하고 휴대폰에서만 깨진다.
- 방향 버튼 4개 안은 채택하지 않는다(화면을 차지하고 게임 느낌이 덜하다).

## 6. 렌더링 **[필수]**

### DOM으로 렌더링한다. canvas가 아니다.

근거:

1. **타일이 최대 16개다.** DOM 노드 16개 갱신은 성능 문제가 아니다. canvas의 유일한 장점(대량 오브젝트)이 여기선 없다.
2. **다크 모드가 조용히 깨지지 않는다.** 이 프로젝트의 테마는 `variables.css`의 커스텀 프로퍼티를 값만 바꿔 구현된다. DOM은 클래스에 붙은 `background: var(--tile-8-bg)`가 테마 전환 시 자동으로 다시 계산된다. canvas는 색을 JS로 읽어(`getComputedStyle`) 직접 칠해야 하고, 테마 토글 시 재드로우를 걸어주지 않으면 **에러 없이 옛날 색으로 남는다.** 정확히 이 프로젝트가 경계하는 종류의 실패다.
3. **접근성 트리가 공짜다.** canvas 안의 숫자는 스크린 리더에 존재하지 않아 병렬 DOM 표현을 따로 만들어야 한다. DOM이면 셀 자체가 읽힌다.
4. **라이브러리 금지 제약과 잘 맞는다.** canvas는 텍스트 정렬·둥근 모서리·DPI 스케일링을 전부 손으로 짜야 한다. CSS는 이미 있다.

### 구조

- 배경 격자: `.board__cell` 16개(빈 칸 표시용, 고정).
- 타일: 값이 있는 칸에만 `.tile.tile--{값}` 요소. 이동할 때마다 타일 레이어를 다시 그린다(타일 신원 추적 없음).
- 레이아웃은 `display: grid`, 셀은 `aspect-ratio: 1`로 정사각형 유지. 보드 폭은 `min(100%, ...)` 로 `--page-width` 안에 들어가게 한다.

### 애니메이션 범위 **[필수]**

- 새로 생긴 타일: `tile--new` 클래스로 scale-in (약 120ms).
- 병합된 타일: `tile--merged` 클래스로 pop (약 120ms).
- `@media (prefers-reduced-motion: reduce)`에서 두 애니메이션 모두 제거한다.

### 슬라이드 애니메이션 **[선택]**

타일이 실제로 미끄러지는 연출은 타일마다 고유 id를 유지하고 이동 전후 좌표로 `transform: translate`를 계산해야 한다. 코드량이 대략 두 배가 되고 병합 시 타일 2개가 1개로 합쳐지는 처리가 까다롭다. **v1에서는 하지 않고, 위 두 애니메이션만으로 피드백을 준다.**

### 색상 토큰 설계

타일 색을 하드코딩할 수 없다. 그렇다고 11단계 × (배경/글자) × 3개 블록(`:root`, `[data-theme="dark"]`, `prefers-color-scheme` 폴백)을 전부 나열하면 66줄이 중복된다. **여기에 함정이 있다: `variables.css:52-63`의 no-JS 폴백 블록은 다크 토큰을 통째로 복제하고 있어서, `[data-theme="dark"]`에만 토큰을 추가하면 JS가 꺼진 다크 모드에서만 색이 틀어진다.**

제안: 명도 램프를 토큰 3~4개로 파라미터화한다.

```
:root {
  --tile-hue: 36; --tile-sat: 72%;
  --tile-l-base: 92%;      /* 값 2 타일의 명도 */
  --tile-l-step: 6%;       /* 단계마다 어두워지는 폭 */
  --tile-fg-low:  <어두운 글자색>;   /* 밝은 타일 위 */
  --tile-fg-high: <밝은 글자색>;     /* 어두운 타일 위 */
  --tile-2-bg: hsl(var(--tile-hue) var(--tile-sat) calc(var(--tile-l-base) - 0 * var(--tile-l-step)));
  --tile-4-bg: hsl(var(--tile-hue) var(--tile-sat) calc(var(--tile-l-base) - 1 * var(--tile-l-step)));
  ... (2048까지)
}
[data-theme="dark"] { --tile-l-base: 20%; --tile-l-step: -5%; --tile-fg-low: <밝은>; --tile-fg-high: <어두운>; }
```

- 커스텀 프로퍼티의 `var()`는 선언된 요소(여기선 `html`)에서 계산되고, `[data-theme="dark"]`도 같은 `html` 요소에 적용되므로 램프가 다크 값으로 다시 계산된다.
- 다크 블록 2곳에 추가할 줄이 **4줄씩**으로 줄어 폴백 블록 누락 위험이 크게 준다.
- 글자색은 램프 방향에 따라 낮은 값/높은 값 타일에서 뒤바뀌는데, `--tile-fg-low`/`--tile-fg-high`의 **값만 서로 바꾸면** 규칙(어떤 클래스가 어떤 토큰을 쓰는지)은 그대로다. "다크 모드는 규칙이 아니라 값만 바꾼다"는 원칙과 맞는다.
- **[결정됨 — 램프 파라미터화를 채택한다.]** 단계별 나열은 색감 조율에 유리하지만, 세 블록 중 하나를 빠뜨렸을 때 JS 꺼진 다크 모드에서만 조용히 깨진다. 그 실패 방식이 이 프로젝트에서 가장 잡기 어려운 종류라 램프를 택한다.
- 램프는 2048 특유의 베이지 → 주황 계열을 근사하도록 hue/saturation을 맞춘다. 색감이 확연히 어긋나면 리뷰에서 지적하고, 그때 나열 방식으로 바꾸는 것은 별도 작업으로 다룬다.
- **명도 대비 4.5:1 이상**을 라이트/다크 양쪽 끝 단계에서 확인한다(§9).

## 7. 접근성 **[필수]**

- 키보드만으로 완전히 조작 가능하다: Tab으로 보드 → New Game 버튼 순서로 이동, 보드 포커스 시 방향키로 플레이. 전역 `:focus-visible`(`base.css:83`)이 포커스 링을 제공한다.
- 보드: `<div class="board" role="grid" tabindex="0" aria-label="2048 board">`, 행은 `role="row"`, 칸은 `role="gridcell"`. 각 칸에 `aria-label`로 값 또는 "empty"를 준다.
- **점수 변화 알림**: 시각적으로 숨긴 `aria-live="polite"` 영역 하나(`#game-status`)를 두고, 이동이 실제로 일어났을 때만 `"Score 24, best 512"` 형태로 갱신한다.
  - 알림 지점은 **한 곳뿐이어야 한다.** 점수 숫자 자체에도 `aria-live`를 걸면 같은 내용이 두 번 읽힌다.
  - 이동이 없었던(벽에 막힌) 입력에서는 갱신하지 않는다. 조용한 것이 정보다.
- 승리/패배: 같은 라이브 영역 또는 별도 `role="status"`로 알리고, 오버레이의 "New Game" 버튼으로 포커스를 옮긴다. 게임이 끝났는데 보드에 포커스가 남아 방향키가 먹지 않으면 키보드 사용자는 갇힌다.
- 모든 조작 요소는 진짜 `<button type="button">`이다.
- no-JS 폴백: `layout.css:46-50`의 `.js` 클래스 패턴을 재사용해, JS가 없으면 보드를 숨기고 "This game requires JavaScript." 문구를 보인다. JS가 안 도는데 죽은 격자만 보이는 상황을 막는다.
- 도움말: 조작법(방향키)을 화면에 텍스트로 표시한다. 아이콘만으로 설명하지 않는다.

### UI 문구 언어 **[결정됨 — 영어]**

사이트 chrome이 영어이고(`SITE.title = 'My Blog'`, "Back to all posts") `site.lang = 'en'`이므로 게임 UI도 영어로 통일한다.
`aria-label`과 라이브 영역 문구까지 전부 영어다. 페이지에 `lang="ko"`가 필요한 요소는 없다.

표준 문구: `Score`, `Best`, `New Game`, `Keep going`, `You win!`, `Game over`, `Use arrow keys to move tiles.`, `This game requires JavaScript.`


#### 계약 2 — 코어 API (B가 제공, C가 소비)

전역 `window.Game2048Core`에 붙인다. 모듈(`type="module"`)을 쓰지 않는 이유: 이 프로젝트에는 번들러가 없고, 모듈 간 상대 경로 import는 "모든 경로는 `href()`를 통과한 절대경로" 규칙과 어긋나 보인다. IIFE + 전역 하나가 기존 `theme-toggle.js` 스타일과도 일치한다.

```
createGame(rng?)                     → state
move(state, direction)               → { moved, state, gained, merged[], spawn }   (순수: state를 변형하지 않는다)
collapseLine(line)                   → { line, gained, mergedSlots }               (테스트 대상)
hasMoves(grid)                       → boolean
isWon(grid)                          → boolean
```

`rng`는 주입 가능해야 한다(테스트 결정성).

## 9. 테스트 계획 (Review 단계)

### 9.1 코어 단위 테스트 — `node scripts/test-2048.js` **[필수]**

병합 규칙은 눈으로 확인하기 어렵다. 브라우저에서 우연히 맞아 보이는 경우가 많아 **반드시 자동 테스트로 못 박는다.** `node:assert` + `node:test`만 쓰고 의존성을 추가하지 않는다(`serve.js`가 세운 선례).

코어가 브라우저 전역 IIFE이므로 Node에서 직접 import할 수 없다. 테스트는 `node:fs`로 파일을 읽고 `node:vm`의 컨텍스트에서 실행해 `Game2048Core`를 꺼낸다. 이렇게 하면 프로덕션 파일에 테스트용 export 분기를 넣지 않아도 된다.

검증 항목:

- `collapseLine` — §3.2 표 6케이스 전부. 특히 `[2,2,4,0] → [4,4,0,0]`(이중 병합 금지)과 `[4,4,4,4] → [8,8,0,0]`.
- `move` — 비대칭 고정 격자 하나로 4방향 각각의 결과를 스냅샷 비교. 방향별 인덱스 매핑이 틀리면 여기서 잡힌다.
- 변화 없는 이동에서 `moved === false`이고 **새 타일이 생기지 않는지.**
- 점수 누적이 병합 값의 합과 일치하는지.
- `hasMoves` — 꽉 찼지만 인접 동일 쌍이 있는 격자에서 `true`, 완전 교대 격자에서 `false`.
- `isWon` — 2048 생성 시점.
- 시드 고정 `rng`로 새 타일 값 분포가 2/4만 나오는지, 빈 칸에만 생기는지.

### 9.2 빌드·경로 검증 **[필수]**

배포 사이트에서만 나는 404를 로컬에서 잡기 위한 절차다.

1. `npm run build` → `dist/games/2048/index.html` 존재 확인, `dist/styles/game-2048.css`·`dist/scripts/game-2048-*.js` 존재 확인.
2. `BASE_PATH=/my-blog npm run build` 후 게임 페이지의 모든 `href=`/`src=` 값을 뽑아 **전부 `/my-blog/`로 시작하는지** 확인. 하나라도 `/styles/`로 시작하면 배포 시 죽는다.
3. `npm run dev`로 `http://localhost:4321/games/2048/` 접속 확인.

### 9.3 브라우저 수동 체크리스트 **[필수]**

- 키보드만으로 처음부터 게임 오버까지 진행 가능.
- 방향키로 페이지가 스크롤되지 않는다(보드 포커스 시). 보드 밖 포커스에서는 스크롤이 정상 동작한다.
- 게임 중 다크 모드 토글 → 타일 색이 즉시 따라간다.
- 새로고침 후 최고 점수 유지, 프라이빗 모드에서 에러 없이 동작(콘솔 확인).
- 콘솔 에러/경고 0건.
- `prefers-reduced-motion: reduce`에서 애니메이션 없음.
- 스크린 리더(VoiceOver)로 이동 후 점수 안내가 **한 번만** 읽히는지.
- 명도 대비: 라이트/다크 각각에서 최저 단계(2)와 최고 단계(2048) 타일의 글자 대비 ≥ 4.5:1.
- 좁은 화면(375px)에서 보드가 잘리지 않는다.

## 10. 하지 않을 것

의도적 제외. 나중에 원하면 별도 작업으로 추가한다.

- **되돌리기(undo)** — 이전 상태 스택 관리가 필요하고, 요구사항에 없다.
- **진행 중인 판 저장/복원** — 최고 점수만 저장한다. 새로고침하면 새 판이다.
- **타일 슬라이드 애니메이션** — §6 참조. 타일 신원 추적 비용 대비 효용이 낮다.
- **보드 크기 선택(3×3, 5×5) UI**.
- **AI 솔버, 힌트, 자동 플레이**.
- **서버 리더보드** — 정적 사이트에 백엔드가 없다.
- **사운드**.
- **애니메이션 라이브러리·프레임워크 도입** — 프로젝트 전제 위반.
- **`assets/` 자원 파이프라인 일반화(번들링/최소화)** — 이번 작업의 목적이 아니다.
- **터치 방향 버튼 4개** — 스와이프로 대체한다(§5.3).
- **WASD 키** — [선택]으로 남긴다.
