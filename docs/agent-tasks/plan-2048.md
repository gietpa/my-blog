# 지침: 2048 게임 spec.md 작성

## 역할

너는 **Plan 단계** 서브에이전트다. 설계 문서 하나를 쓰는 것이 전부다.

## 수정 허용 범위

**`docs/spec-2048.md` 한 파일만 생성한다.**

그 외 어떤 파일도 만들거나 고치지 않는다. 특히 구현 코드(`.js`, `.css`, `.html`)를 한 줄도 쓰지 않는다.
구현은 사용자 승인 후 별도의 Work 서브에이전트가 한다. 코드를 미리 쓰면 승인 절차를 무의미하게 만든다.

읽기는 저장소 어디든 자유롭게 해도 된다.

## 만들 것

방향키로 숫자 타일을 밀어 합치는 2048 퍼즐 게임. 점수판 포함.
사용자가 명시한 요구사항은 이 세 가지(방향키 조작 / 타일 병합 / 점수판)뿐이다.
나머지는 네가 제안하되, 무엇이 필수이고 무엇이 선택인지 spec에서 구분해서 표시하라.

## 먼저 조사할 것

이 저장소는 마크다운을 정적 블로그로 굽는 도구다. 게임은 원래 이 파이프라인에 없던 것이므로,
**추측하지 말고 코드를 읽고 판단하라.**

1. `scripts/build.js` — 빌드가 무엇을 `dist/`로 내보내는지. 현재 `assets/css` → `dist/styles`,
   `assets/js` → `dist/scripts` 복사가 전부다. 게임 파일이 어떻게 나갈지는 아직 답이 없다.
2. `scripts/lib/templates.js` — 페이지 HTML이 만들어지는 방식, `href(site, ...)` 헬퍼.
3. `assets/css/variables.css` — 테마 토큰. 색을 새로 만들기 전에 여기 있는 것을 먼저 쓸 수 있는지 보라.
4. `.github/workflows/deploy.yml` — 배포 경로.

### 지금 CLAUDE.md에 없지만 여전히 유효한 제약

CLAUDE.md는 방금 작업 프로세스 문서로 교체되었다. 이전 판에 있던 기술 제약은 **코드에는 그대로 살아 있다.**
반드시 읽고 spec에 반영하라:

```bash
git show 54df309:CLAUDE.md
```

이 중 최소한 다음은 게임에도 그대로 적용된다. 어겨도 에러가 안 나고 조용히 깨지는 것들이라 특히 중요하다:

- **브라우저로 나가는 코드에 프레임워크·라이브러리 금지.** 순수 HTML/CSS/바닐라 JS. 이건 이 프로젝트의 핵심 전제다.
- **모든 경로는 `href(site, ...)`를 통과시킨 사이트 절대경로.** 상대경로 금지. 빼먹으면 배포된 사이트에서만 404가 나고 로컬에서는 멀쩡해 보인다.
- **테마 색은 `variables.css`의 커스텀 프로퍼티로만.** 하드코딩 금지. 다크 모드는 규칙이 아니라 값만 바꾼다.
- **`dist/`는 매 빌드마다 통째로 지우고 다시 만든다.** 게임 자원도 원본이 저장소에 있어야 한다.
- 접근성: 시맨틱 태그, 충분한 명도 대비, 진짜 `<button>`, `:focus-visible`.

## spec.md에 담을 것

1. **배치 결정** — 게임 파일이 저장소 어디에 있고 어떻게 `dist/`로 나가는가. 최소 2개 안을 장단점과 함께 제시하고
   하나를 추천하라. 빌드 스크립트를 고쳐야 한다면 어디를 어떻게 고치는지 구체적으로.
   URL이 무엇이 되는지도 명시하라 (배포 사이트는 `/my-blog/` 하위에서 서빙된다).
2. **게임 규칙** — 격자 크기, 새 타일 생성 규칙(값과 확률), 승리/패배 판정 조건.
3. **이동·병합 알고리즘** — 한 줄을 미는 연산을 의사코드로. 특히 **한 번의 이동에서 이미 병합된 타일이
   다시 병합되지 않아야 한다**(`[2,2,4]`를 왼쪽으로 밀면 `[4,4]`이지 `[8]`이 아니다). 2048 구현에서
   가장 흔히 틀리는 지점이니 spec에서 명시적으로 다뤄라. 4방향을 각각 따로 구현할지, 회전·전치로
   한 방향만 구현하고 재사용할지도 정하라.
4. **점수** — 점수 계산 방식, 최고 점수 저장 여부와 저장소(localStorage를 쓴다면 키 이름까지).
5. **입력** — 방향키 처리. 페이지 스크롤을 막을지, 어떤 조건에서 막을지. 모바일 터치는 필수인지 선택인지 판단해서 표시.
6. **렌더링** — DOM인지 canvas인지 정하고 **왜 그쪽인지** 근거를 대라. 애니메이션 범위도.
7. **접근성** — 키보드만으로 조작 가능한가, 점수 변화를 스크린 리더에 어떻게 알릴 것인가.
8. **파일 목록** — 만들 파일과 각각의 책임. Work 단계에서 서브에이전트를 나눈다면 범위가 겹치지 않게 나뉠 수 있는 구조인지.
9. **테스트 계획** — Review 단계에서 무엇을 어떻게 확인할지. 병합 규칙처럼 눈으로 보기 어려운 것은 어떻게 검증할지.
10. **하지 않을 것** — 의도적으로 범위에서 뺀 것들.

## 태도

- 결정에는 근거를 붙여라. "DOM으로 렌더링한다"가 아니라 "타일 수가 16개뿐이고 CSS 트랜지션과 접근성 트리를
  그대로 쓸 수 있어서 DOM으로 렌더링한다"처럼.
- 확실하지 않은 것은 확실한 척하지 말고 spec에 "결정 필요"로 남겨라. 사용자가 승인 단계에서 판단한다.
- 분량보다 정확성이다. 코드를 읽고 쓴 문장만 남겨라.

## 끝나면

spec의 핵심 결정 사항과, 사용자 판단이 필요한 열린 질문을 요약해서 보고하라.
