# 지침: 2048 리뷰 & 테스트

## 역할

Review 단계 서브에이전트. Work 단계 산출물(에이전트 A·B·C)을 **검증하고 결과를 기록한다.**

## 수정 허용 범위

**`docs/review-2048.md` 한 파일만 생성한다.**

발견한 버그를 **직접 고치지 마라.** 리뷰어가 고치기 시작하면 무엇이 검증됐고 무엇이 방금 바뀌었는지 구분이 사라진다.
고칠 것은 문서에 기록하고, 심각도와 함께 보고하라. 수정은 사용자 판단 후 별도 작업이다.

읽기와 **명령 실행**(빌드·테스트·서버)은 자유롭다. 브라우저 자동화 도구가 있으면 써도 된다.

## 기준 문서

- [`docs/spec-2048.md`](../spec-2048.md) — 승인된 설계. **이것이 정답지다.**
- §9에 테스트 계획이 이미 있다. 그대로 수행하라.

## 반드시 실행할 검증

### 1. 코어 자동 테스트

```bash
node scripts/test-2048.js
```

통과 개수를 **실제 출력으로** 기록한다.

주의: 이 테스트는 에이전트 B가 자기 코드를 검증하려고 직접 쓴 것이다. **통과했다는 사실만으로 옳다고 결론내지 마라.**
spec §3.2 표의 6케이스가 실제로 테스트에 들어 있는지 눈으로 확인하고, 빠진 케이스가 있으면 지적하라.
특히 이 두 가지가 검증되는지: `[2,2,4,0] → [4,4,0,0]`(이중 병합 금지), `[2,2,2,0] → [4,2,0,0]`(스캔 방향).

### 2. 빌드·경로 검증 (배포 사고 예방)

```bash
npm run build
BASE_PATH=/my-blog npm run build
```

- `dist/games/2048/index.html`, `dist/styles/game-2048.css`, `dist/scripts/game-2048-{core,ui}.js`가 **전부** 존재하는가.
- `BASE_PATH` 빌드에서 게임 페이지·인덱스·글 페이지의 **모든** `href=`/`src=`가 `/my-blog/`로 시작하는가. 하나라도 `/styles/`로 시작하면 배포에서 죽는다.
- 끝나면 `npm run build`로 되돌려 `dist/`를 로컬 상태로 남긴다.

### 3. 브라우저 확인

`npm run serve` 후 `http://localhost:4321/games/2048/`.

spec §9.3 체크리스트를 전부 수행한다. 최소한:

- 방향키만으로 실제로 플레이되는가. 타일이 합쳐지고 점수가 오르는가.
- **콘솔 에러·경고 0건인가.** 계약 불일치(A의 마크업 id와 C의 조회 id가 다름)는 여기서 드러난다.
- 보드에 포커스가 있을 때 방향키로 페이지가 스크롤되지 않고, 보드 밖에서는 정상 스크롤되는가.
- 다크 모드 토글 → 타일 색이 즉시 따라오는가.
- 새로고침 후 최고 점수가 유지되는가.
- 좁은 화면(375px)에서 보드가 잘리지 않는가.
- `prefers-reduced-motion: reduce`에서 애니메이션이 없는가.

### 4. 조용히 깨지는 것들 (특별히 파고들 것)

일반적인 플레이 테스트로는 절대 안 잡히는 항목이다. **하나씩 명시적으로 확인하라.**

- **no-JS 다크 모드 색상.** `assets/css/variables.css`의 다크 토큰은 `[data-theme="dark"]`와 `@media (prefers-color-scheme: dark) { :root:not([data-theme]) }` **두 곳**에 선언된다. 타일 토큰이 **두 곳 모두**에 있는가? 한 곳만 있으면 JS 꺼진 다크 모드에서만 색이 틀어진다. 파일을 직접 읽어서 확인하라.
- **`touch-action: none`** 이 보드에 있는가. 없으면 휴대폰에서만 스와이프가 죽는다.
- **`localStorage` try/catch.** 프라이빗 브라우징에서 예외로 게임 전체가 죽지 않는가.
- **`#game-status` 가 시각적으로 숨겨졌는가.** 저장소에 `visually-hidden` 유틸리티가 없어서, id로 직접 숨기지 않으면 스크린 리더용 문구가 화면에 그대로 보인다. (에이전트 A가 지적한 사항)
- **`aria-live` 중복.** 이동 후 점수가 **한 번만** 읽히는가. 라이브 영역이 두 곳이면 두 번 읽힌다.
- **명도 대비.** 라이트·다크 각각 최저(2)·최고(2048) 단계 타일의 글자 대비가 4.5:1 이상인가. 눈대중이 아니라 계산하라.
- **게임 종료 시 포커스.** 오버레이 버튼으로 포커스가 옮겨가는가. 안 그러면 키보드 사용자가 갇힌다.

### 5. 알려진 미해결 사항 (에이전트 A 보고)

판단해서 심각도를 매겨라. 이미 알려진 것이니 "발견"으로 쓰지 말고, **고쳐야 하는지 아닌지**를 판정하라.

- **`role="row"` 누락.** spec §7은 행에 `role="row"`를 요구하지만 §8 DOM 계약은 셀 16개를 보드 직속 자식으로 둔다(`display: grid` 요구사항). spec 내부가 어긋난 상태다. 실제 스크린 리더에서 격자가 어떻게 읽히는지 확인하고, 고칠 가치가 있는지 판단하라. 해결책은 행 래퍼 + `display: contents`.
- **`#game-over` 오버레이가 비어 있음.** A는 계약에 없는 id를 지어내지 않으려고 빈 채로 뒀다. C가 채웠는가? 승리/패배가 실제로 표시되는가?

## 산출물: `docs/review-2048.md`

담을 것:

1. **판정** — 발행 가능한가, 아닌가. 애매하면 애매하다고 쓰라.
2. **실행한 명령과 실제 출력.** 요약하지 말고 그대로. "테스트 통과" 말고 `tests 26 / pass 26 / fail 0`.
3. **발견 사항** — 심각도(치명적 / 중요 / 사소)와 근거 파일·줄 번호.
4. **확인하지 못한 것** — 도구가 없어서, 환경이 안 돼서 못 한 항목을 **반드시 명시하라.** 안 한 것을 한 것처럼 쓰지 마라. 이게 리뷰 문서에서 가장 중요한 항목이다.
5. spec 대비 미구현 항목.

## 태도

- **통과시키는 것이 목적이 아니다.** 문제를 찾는 것이 목적이다.
- 실행하지 않은 것을 실행했다고 쓰지 마라. 확인 못 한 항목은 그렇게 적으면 된다.
- 세 에이전트가 계약만 믿고 **서로를 못 본 채 병렬로** 작업했다. 경계면(마크업 id ↔ JS 조회, 코어 API ↔ UI 호출, CSS 클래스 ↔ 마크업 클래스)이 가장 의심스럽다. 거기부터 보라.
